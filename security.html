Privacy & Security

How student information is protected

The registration form is designed around data minimization, strict Firestore access rules, and controlled administrative access for approved school workflows.

Minimal data collection

The form only collects information needed to schedule and administer the blood drive. It does not collect passwords, blood type, medical screening answers, IP address, browser fingerprint, or device IDs.

No public registration reads

Firestore rules deny browser reads, updates, and deletes for registration records. Public visitors can submit a validated registration, but cannot browse or download student records.

Validated writes

Security rules allow registration creation only when the submitted document matches the approved field list, type checks, size limits, eligibility confirmations, known appointment slots, and server timestamp requirements.

Atomic slot protection

Appointment capacity is tracked in separate non-PII slot counter documents. Transactions reserve a spot and create the registration together, while rules prevent overbooking by only allowing exact +1 counter changes up to capacity.

FERPA-aware design

The app uses least-privilege access and avoids exposing student education records publicly. Final FERPA compliance still depends on district-approved policies, staff access controls, retention practices, contracts, and review before use with real student data.

Approved reporting access

Google Apps Script reporting can access Firebase using a district-controlled service account or approved backend credential. Server-side administrative credentials bypass browser rules, so they should be stored only in Apps Script properties or a secure backend—not in frontend code.

Important: never place Firebase Admin SDK credentials, service-account private keys, or privileged tokens in this public website. Keep reporting credentials server-side and limit them to approved organizers.
